# ПОМОГАТОР VPN v0.3.2

Русскоязычное WPF-приложение для Windows 10 x64. В комплект входят .NET и Xray-core 26.11.9. Учётная запись и права администратора не требуются. [Исходники Xray-core и лицензия MPL 2.0](https://github.com/XTLS/Xray-core/tree/v26.11.9)

## Запуск

1. Распакуйте артефакт `PomogatorVpn-0.3.2-win-x64` успешного запуска GitHub Actions. Запустите `PomogatorVpn.exe` из этой папки.
2. Вставьте ссылку VLESS, откройте файл или добавьте подписку HTTPS. Выберите сервер в списке и нажмите круглую кнопку.
3. После статуса **Подключён и проверен** в карточке появятся локальный адрес и время сеанса. По умолчанию приложение запускает HTTP-прокси на `127.0.0.1`. В полном профиле также может быть локальный SOCKS.
4. Через **Настройки** можно выбрать системный прокси Windows. Приложение применит его только после явного подтверждения и успешной проверки VLESS.
5. Сворачивание оставляет сеанс в трее. Значок и подпись отражают состояние. Меню трея позволяет открыть окно, отключиться и выйти. Крестик и команда **Выход** завершают сеанс.

Состояния в окне и трее: серый **Отключён**, жёлтый **Подключается**, зелёный **Подключён и проверен**, жёлтый **Связь нестабильна**, красный **Ошибка подключения**, голубой **Отключается**. Анимация ожидания учитывает системную настройку анимаций. В настройках можно включить запуск приложения в трее вместе с Windows. По умолчанию автозапуск выключен. Приложение после автозапуска ждёт выбора пользователя и не подключает VPN само.

## Импорт EasyGoVPN и Xray

При открытии клиентского JSON выберите режим явно:

- **Полный профиль** сохраняет совместимые DNS, порядок и правила маршрутизации, теги и исходящие подключения VLESS, Freedom (`direct`), Blackhole (`block`) и DNS. Входы HTTP и SOCKS создаются заново на свободных портах loopback с исходными тегами и совместимыми настройками распознавания протоколов. Входы с учётными данными, балансировщики, внешние файлы правил и произвольные исходящие протоколы не поддерживаются. Обычные запросы могут идти напрямую, если такое правило было в полном профиле.
- **Упрощённый профиль** переносит первый VLESS-сервер и его параметры. Маршрутизация, DNS и остальные исходящие подключения из файла опускаются. Если полный профиль несовместим, приложение сообщит об ошибке. Упрощённый вариант можно выбрать при повторном импорте.

Поддерживаются TLS, REALITY, SNI, fingerprint, Vision для TCP, TCP, WebSocket, gRPC, HTTPUpgrade и XHTTP. REALITY работает с TCP, XHTTP и gRPC. Импорт TCP + REALITY поддерживает `serverName`, `publicKey` (или `password` в новой схеме Xray), `shortId`, UUID и `flow`. Профили без TLS или REALITY предназначены только для loopback-тестов.

Подписки читаются напрямую с указанного HTTPS-адреса. Поддерживаются списки VLESS в UTF‑8 или Base64 и клиентский JSON. Допускаются до трёх перенаправлений HTTPS на том же хосте и порту, включая относительные. Другой хост, смена протокола и цепочки с циклом отклоняются. Ответы 401, 403, 404, 410, 429 и другие HTTP-ошибки выводятся с указанием кода. Лимит загрузки 1 МБ, лимит списка 100 профилей.

## Диагностика

**Проверить соединение** открывает панель с отдельными результатами Xray, локального прокси, контрольного HTTPS и WinINet. **Измерить задержку** замеряет время установления TCP-соединения с сервером, включая разрешение имени при необходимости. Это не ICMP и не задержка до сайта через VPN.

Зелёный статус появляется после проверки процесса, локального транспорта и HTTPS через выбранный VLESS. В полном профиле прокси проверяется отдельным входом, для которого закреплён VLESS. В режиме TUN контрольный запрос использует сетевой стек Windows без системного прокси. Адрес источника и выбранный маршрут должны соответствовать интерфейсу Wintun.

Если Xray не подтвердил порт вовремя, приложение до двух раз выбирает новые порты. Фоновый контроль не меняет состояние кнопки ручной проверки.

Три контрольных адреса Google, Cloudflare и Microsoft проверяются параллельно с лимитом 5 секунд на адрес. Успешного ответа от одного достаточно. Активный сеанс проверяется каждые 30 секунд. После сбоя всех адресов отображается **Связь нестабильна**, проходят ещё два раунда через 5 и 15 секунд. После третьего сбоя сеанс остаётся активным без новых автоматических HTTPS-проб. **Проверить соединение** запускает новый цикл. Выход Xray, потеря локального транспорта, интерфейса или маршрута TUN обрабатываются отдельно. В последнем случае приложение завершает сеанс, чтобы восстановить настройки. Автоматическое переподключение отсутствует.

В диагностике показаны TCP до сервера и время проверочного HTTPS отдельно. Внешний IP запрашивается через ipify. В TUN результат сравнивается с отдельным запросом через локальный VLESS. Несовпадение может зависеть от выхода поставщика и отображается как отдельный результат. Экспорт не включает внешний IP, URL подписок, ключи, UUID и вывод Xray.

## Экспериментальный режим TUN

Для TUN нужны Windows 10 22H2 x64 (19045) или новее, `wintun.dll` из комплекта и согласие на UAC под той же учётной записью Windows. Xray создаёт адаптер Wintun и при необходимости устанавливает драйвер. Повышение применяется к помощнику TUN, а режимы прокси запускаются с правами пользователя. [Документация Xray TUN](https://github.com/XTLS/Xray-core/blob/v26.11.9/proxy/tun/README.md) · [Лицензия бинарного Wintun](https://www.wintun.net/)

Xray передаёт трафик Wintun напрямую в выбранный VLESS. Перед созданием Wintun отдельная HTTPS-проверка подтверждает профиль с тем же IPv4 сервера. Публичный IPv4 направляется через выбранный VLESS. За TUN остаются локальные диапазоны, служебный трафик, loopback и закреплённый IPv4 сервера EasyGoVPN. IPv6 блокируется на время сеанса средствами Windows Filtering Platform. DNS назначается новому интерфейсу и идёт через туннель. На остальных интерфейсах Xray временно фильтрует внешний DNS и публичный трафик. Политика учитывает исключения Xray для loopback, DHCP и локального служебного трафика. Она действует пока процесс TUN удерживает динамические фильтры и не является постоянным kill switch. Режим локального прокси применяет маршрутизацию полного профиля. Системный прокси направляет трафик в проверенный VLESS. TUN использует тот же VLESS для публичного трафика и отдельную DNS-политику.

Приложение отклоняет запуск при обнаружении активного VPN-интерфейса, UBoost или занятого WinINet, а при изменении рабочего маршрута или IPv4 сервера предлагает переподключиться. Распознавание стороннего клиента эвристическое. Доступность DNS устройств за ICS зависит от того, как они используют системный DNS компьютера. Конфигурация PPPoE, ICS и Wi-Fi не меняется.

Маршруты и DNS записываются только на уникальный виртуальный адаптер. Перед запуском исходное состояние и признаки собственного интерфейса сохраняются через DPAPI. При отключении Xray получает штатный сигнал завершения. Если интерфейс остался после сбоя, следующий запуск предлагает восстановление. Оно удаляет только опознанный Wintun с ожидаемыми адресами, DNS и маршрутами. Если подтверждение не удаётся или параметры расходятся, запись сохраняется для ручной проверки.

#### Что показывает отчёт TUN в версии 0.3.2

После запуска Xray приложение до 10 секунд ждёт, пока Windows покажет ожидаемый Wintun, готовый IPv4-адрес, назначенный DNS и нужные маршруты. Для маршрутов проверяются выбранные Windows интерфейсы к VPN-серверу, назначенному DNS и контрольному публичному IPv4. Отчёт указывает фактические параметры, длительность ожидания и первый этап, на котором запуск не подтвердился.

Затем приложение сравнивает три отдельных результата. Оно отправляет DNS-запрос напрямую к назначенному серверу через Wintun, запрашивает IPv4 контрольного имени у системного DNS Windows и проверяет HTTPS через сокет Wintun. HTTPS по контрольному IP проверяет трафик без разрешения имени. При недоступности этого узла используются дополнительные контрольные HTTPS-имена. Код WinSock, код ответа DNS, истечение ограничения времени и сбой HTTPS отражаются отдельно. Успех HTTPS или локального прокси сам по себе не переводит TUN в состояние «Подключён».

Экспорт сохраняет итог предыдущей попытки после её остановки до начала следующего подключения. В отчёт входят GUID и индекс собственного Wintun, его IPv4 и DNS, индексы маршрутов, этап отказа, время проверок, итог восстановления и доступная причина завершения Xray. Содержимое профиля и сырые сообщения Xray в отчёт не входят.

## Безопасная проверка на Windows 10

1. Сначала проверьте v0.3.2 в **Локальном прокси** с вашим профилем. На Windows отдельно убедитесь, что PPPoE подключён, а телефон открывает сайт через Wi-Fi. Сохраните отчёт исходной сетевой диагностики.
2. По возможности начните с изолированной Windows 10 VM. На рабочем ПК завершите другие VPN только вручную, если сами согласны на паузу. Если UBoost нужен для поддержания связи, оставьте его активным и проверьте предупреждение либо используйте локальный режим.
3. После явного подтверждения включите TUN. Проверьте имя состояния, результат HTTPS и внешний IP. Сравните их с запросом через локальный VLESS. Проверьте DNS, IPv4 и отсутствие внешнего IPv6 отдельно. Проверьте телефон, поскольку временный DNS-фильтр может влиять на раздачу.
4. Отключите TUN и проверьте исчезновение интерфейса ПОМОГАТОР, доступность PPPoE и работу телефона. Сравните исходные маршруты и DNS с результатом после сеанса. Аварийное завершение впервые проверяйте только в VM.
5. При оставшемся интерфейсе откройте приложение заново, подтвердите предложенную проверку и сохраните результат. Если идентичность интерфейса или его параметры не подтверждены, приложение оставит запись восстановления для разбора.

Для проверки можно использовать команды только для чтения. Запустите их до TUN, во время сеанса и после отключения. Во время сеанса IPv4 должен отвечать через VPN, а прямая проверка IPv6 должна завершиться ошибкой. Не передавайте полученные адреса без необходимости.

```powershell
Resolve-DnsName www.cloudflare.com -Type A -DnsOnly
curl.exe -4 --noproxy "*" --max-time 10 https://api.ipify.org/
curl.exe -6 --noproxy "*" --max-time 10 https://api64.ipify.org/
Get-NetAdapter -IncludeHidden | Where-Object Name -like 'PmtVpn-*'
```

## Настройки Windows и восстановление

В системном режиме меняются только параметры прокси WinINet текущего пользователя для единственного активного PPPoE-подключения по данным Windows RAS, либо для LAN, если RAS не используется. При отключении восстанавливается тот же источник настроек. Приложение подтверждает соединение запросом через прокси, выбранный системой, и сверяет внешний IP с запросом через выбранный VLESS. Политики Chrome и расширения могут выбрать другой прокси. Сверьте внешний IP в самом Chrome. Некоторые приложения и PPPoE могут использовать отдельный прокси. При включении автозапуска меняется только запись приложения в HKCU. Kaspersky и UBoost находятся вне управления приложения.

Исходное состояние WinINet сохраняется с DPAPI до изменения. Приложение отклоняет включение, если уже назначен ручной прокси или PAC. Восстановление выполняется только пока текущие параметры совпадают с применёнными. При изменении извне остаётся локальный режим. После аварийного выхода следующий запуск предлагает восстановление с той же проверкой. Job Object Windows завершает дочерний Xray при завершении приложения. Профили шифруются DPAPI в `%LOCALAPPDATA%\PomogatorVpn` и передаются ядру через stdin.

## Сборка и проверки

Из корня репозитория, с .NET SDK 8:

```powershell
dotnet run --project windows/vpn/tests/Tests.csproj -c Release
dotnet publish windows/vpn/app/PomogatorVpn.csproj -c Release -r win-x64 --self-contained true -o windows/vpn/dist
./windows/vpn/scripts/Get-Xray.ps1 -Destination windows/vpn/dist
```

Для интеграционного теста задайте `POMOGATOR_TEST_XRAY` абсолютным путём к Xray из комплекта. Тест использует только синтетические данные и loopback. Проверку реального WinINet через `POMOGATOR_TEST_WININET=1` запускайте только на изолированном Windows-раннере без действующего прокси. Отдельный WPF-тест в CI проверяет шесть состояний и трей и сохраняет PNG при рендеринге 100%, 125% и 150%.

На целевом ПК отдельно проверьте реальный профиль EasyGoVPN, совместимость с вашим сервером и другими клиентами, отображение при системном масштабировании Windows и восстановление при аварийном завершении. CI визуализирует окно в указанном DPI, а переключение масштаба реального дисплея и поведение браузеров с PPPoE проверяются на месте.

Нативный TUN-тест через `POMOGATOR_TEST_TUN=1` предназначен только для изолированного CI с администратором. Он добавляет два маршрута из диапазона документации и фильтр для диапазона документации IPv6, проверяет реальный HTTPS, UDP и DNS-запрос через Wintun, отказ привязки к чужому маршруту, восстановление после остановки и аварийного завершения. Полный охват Интернета, реальный сервер, IPv6-утечки на двухстековом оборудовании и совместимость с PPPoE/ICS требуют отдельной проверки.
